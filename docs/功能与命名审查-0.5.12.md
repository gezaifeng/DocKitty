## 产品结构：哪些是合理的多入口

| 能力 | 版本管理 | 项目管理 | 结论 |
| --- | --- | --- | --- |
| 管理对象 | 一份文档的多份稿件 | 一个项目的文件、文件夹与迭代 | 两个入口有明确用途，不应仅因卡片相似而合并 |
| 编辑文件 | 从库内版本准备独立编辑副本 | 打开关联的原项目文件 | 按此前确认的规则实现，需持续明确提示作用对象 |
| 保留历史 | 新稿首次修改保存生成节点，随后保存更新同一稿 | 明确“记录下一轮”才保留迭代 | 差异是既定产品规则；不能用统一“自动保存”概括 |
| 连线 | 表示前后版本，禁止循环，影响前版本比较 | 普通资料关系可循环；迭代关系另有检查 | 外观编辑可共用，业务含义需要区分 |
| 分类 | 每份文档自己的版本分类 | 项目内共用分类，当前层看板 | 范围不同，符合已确认的需求 |
| 刷新 | 同步独立编辑副本，发现稿喵工作目录根层新文件 | 扫描项目来源，更新当前卡片并移除已删除来源的记录 | 不能都解释为“重新加载页面” |
| 导入入口 | 文件菜单、顶栏、画布菜单、拖放 | 文件菜单、顶栏、画布菜单、拖放 | 正常快捷入口，核心导入服务共用，不是重复存储功能 |
| 连线编辑入口 | 双击或右键打开同一个编辑面板 | 同左 | 已共用 `EdgeEditor`，不存在两套样式编辑规则 |
| 连接操作 | 右键拖线；菜单选择前后连接后点选 | 右键拖线；“连接资料”后点选 | 两种输入方式可以保留，退出和方向提示应一致 |
| 备注 | 稿件备注、连线备注分别保存 | 资料备注、连线备注分别保存 | 是不同对象，不应合并成一个字段 |
| 预览与导出 | 只读预览、临时历史副本、指定位置导出 | 只读预览、指定位置导出、编辑来源 | 不同文件生命周期；应明确区分“查看”“编辑”“导出” |
| 撤回与重做 | 本次启动的可恢复操作 | 同左，复制 / 剪切另校验磁盘文件 | 全局历史服务共用；“撤销覆盖”另属稿件内容修订 |

## 需要处理的问题

P1 表示容易引起操作误解或当前显示与实际不一致；P2 表示一致性、效率与维护问题。这里只给出已找到的证据，不把“未发现”写成“绝对不存在”。

| 编号 | 优先级 | 当前问题 | 建议处理 |
| --- | --- | --- | --- |
| A01 | P1 | 分支 / 路线 / 编辑路线混用；顶栏“查看分支”只筛选，侧栏“当前分支”会切换实际编辑分支 | 统一使用“分支”；分别命名“查看范围”和“编辑分支”，切换提示说明是否改变编辑对象 |
| A02 | P1 | 统计后台已经按唯一分支归属统计，界面却显示“包含共同祖先”；仍有“本路线独有版本”和“共同版本”旧选项 | 修正文案；确认是否把无实际区分度的独有筛选删除。保留独立版本与实际父节点比较；不改回祖先归属 |
| A03 | P1 | “打开当前工作区”按钮实际优先打开独立编辑副本；“保存工作区”与“同步编辑副本”随状态切换，但侧栏同时展示工作区和副本状态 | 按实际文件命名为“打开编辑副本”等；把兼容工作区流程与当前编辑会话清楚分组。不要据名称直接删除旧流程 |
| A04 | P1 | 回收版本确认框承诺关系图保留祖先标记，但当前正常图已过滤掉回收版本；两端不同时在图中，连线也不绘制 | 先修正错误说明；如需祖先占位，应作为单独产品选择。普通筛选下仍保留活跃的独立版本 |
| A05 | P1 | 文档 / 版本回收在“回收内容”，分支回收在设置；右侧“回收版本”与右键“删除版本…”同属删除却开放不同选项 | 统一“移入回收区 / 永久删除”的动词和恢复入口，始终写明管理记录、库内快照、来源文件三个范围 |
| A06 | P1 | 项目刷新覆盖当前受管内容；先刷新后再“记录下一轮”，不能找回刷新前未记录的状态 | 现行为符合明确记录历史的规则。建议在刷新和记录入口解释基准，并提供“先保留本轮再刷新”的明确操作；是否增加此操作需确认 |
| A07 | P2 | 稿件“名称 / 说明 / 分类”和“编辑备注”都可修改同一个版本 note；项目“名称与备注”只修改显示标题，不重命名磁盘文件 | 统一为“编辑版本信息”“版本备注”“关系备注”“显示名称”；保留备注快捷入口，但说明它属于同一字段 |
| A08 | P2 | 两个管理模式切换时组件卸载：版本页返回总览，项目页返回项目列表，原先视图 / 文件夹上下文丢失 | 分别保留各模式的当前项目、文件夹、视图和筛选；切换后回到原位置，删除或迁移后再校验失效位置 |
| A09 | P2 | “复位关系图”恢复缩放和平移，“整理布局”改变节点排布，名称容易让人以为是同一件事 | 改成“重置视角”和“整理卡片布局”；后者支持撤回，前者不改变存储的卡片位置 |
| A10 | P2 | 顶栏“功能”目前主要装外观开关；菜单、按钮和空白右键菜单的可用新建操作不完全对应 | 保留用户指定的“功能”入口，内部按“显示 / 动效”分组；逐项对齐同场景可用动作和禁用原因 |

特别说明：项目来源删除后会移除相关当前和历史卡片，是此前确认的规则；项目普通“移除”不删除来源文件。它们与版本管理的回收区是不同机制，不能擅自统一成一种删除行为。

## MCP 和维护上的边界

- 当前 MCP 有 **15 个工具**，范围是项目库、导入、刷新、明确记录迭代、资料信息、分类、关系、读取与导出。没有把桌面全部功能都暴露出来：版本管理的独立新稿 / 分支 / 统计、全局撤回、新建 Office 文件等没有对应的完整 MCP 操作集。
- MCP 的 `dockitty_update_item` 明确只改显示信息，不改磁盘文件名；没有通用的来源正文写入工具。Agent 可以先用自己的文件工具修改，再调用稿喵刷新或记录迭代。不要把“MCP 写入后刷新”宣传成稿喵已经自带任意文件编辑工具。
- MCP 项目写操作后会刷新来源；这会涉及 A06 的历史基准。后续应让 Agent 说明“更新当前资料”还是“保留迭代”，并返回可在界面定位的操作结果。
- 桌面版本与 MCP 自报版本分别来自不同位置（当前服务器标识仍是 `0.5.4`）。不等于协议已坏，但需要说明应用版本、组件版本和支持的工具，避免客户端误认为版本未升级。
- 旧 `ThemeToggle`、`DocListPanel`、`BranchPanel`、`TimelinePanel`、`EditLoopCard` 等仍保留源码和测试，当前 `MainLayout` 主界面不使用它们。这是维护重复，不是用户面前同时显示两套功能。本轮仅同步其主题名称，没有擅自删除。
- `TODOLIST.md` 既有“已完成”概述，又保留最初的未勾选审计清单。历史验收目标有保留价值，但不适合作为当前唯一进度表。建议后续新增唯一的当前状态表，并让旧记录明确链接过去。

## 建议的后续开发顺序

### 第一批：统一操作语言和范围

先处理 A01–A05、A07、A09。核心是让用户点按钮前就知道：正在查看哪一支、将编辑哪份文件、是否新增历史、删除的究竟是什么。

验收：版本图、统计、侧栏、菜单和帮助使用同一套术语；每个编辑入口显示副本 / 原件身份；回收说明与实际图形一致；“共同祖先”不再误导唯一归属统计；同一动作从不同入口进入具有一致结果。

### 第二批：让两个核心工作流顺畅衔接

保留各模式上下文；加强“编辑 → 刷新当前资料 → 明确记录迭代”的状态说明。先用明确按钮解决刷新前保留基准的问题，是否改变保存政策另行确认。补充当前来源路径、编辑副本路径和历史快照身份，减少找错文件。

验收：切换模式能回到原文件夹和视图；刷新与记录先后次序都能让用户判断结果；源文件修改、缺失、同名导入和已记录快照的状态可分辨；测试只使用隔离文件夹。

### 第三批：寻找、比较和交付成果

优先改进跨项目 / 文稿的名称、备注和分类检索，以及常用 Office 内容预览与比较。结合真实投稿流程展示“这版为什么改、与上一版差在哪、要交给谁”，可先完善现有备注和比较入口，再决定是否增加送审 / 投稿模板。

验收：几十至数百份资料能够按名称 / 备注 / 分类找到；Word / Excel / PPTX 逐项标出保存、预览和比较支持范围；导出稿与选中历史一致，来源文件不被改写。

### 并行底座：数据可靠性、性能和 Agent 验收

补真实 Word / WPS 手工保存证据、占用与写入失败恢复、备份还原和干净设备安装验收；用实测规模评估大量文件和关系图性能。给 MCP 补能力清单和实际工具调用到 UI 结果的追踪，是否扩展到版本管理再按需求确定。

验收：原文件和历史有哈希对照；失败后有明确可恢复路径；MCP 调用结果可在界面定位且重试不重复生成迭代；性能报告写明文件数量、大小、机器和耗时。历史自动化测试通过不能替代真实 Office 或安装 / 卸载验证。

**建议下一版主题是“操作一致性”**：先完成第一批，并补齐 A08 的上下文保留。这样下一次使用能直接感受到流程更清楚、切换更顺畅。
